01 · 等待

在等的是一个 Node 进程，不是 Claude

Claude 启动命令后就空出来了。进程一直等到 Codex 这一轮结束才退出，退出的那一刻，Claude Code 自带的后台任务通知把结果交给 Claude。

Claude Code
派发 自由：继续干活，或停下来 被通知
ask-codex
进程在等，每 3 秒读一次
Codex 桌面
在已有对话里工作
开始几分钟，或几十分钟结束

Claude 在忙

它继续改别的文件、跑别的测试。通知到达后，它接着处理 Codex 的回复。

Claude 停下来了

这一轮已经结束，终端空着，没有人输入。通知会把它自动唤醒，不需要你按回车。

只在结束时通知

中间回复写进 stderr，Claude 想看随时能看，但每条日志不会打断它。

02 · 原理

不新建通道，只借用两端已有的

两端各有一样现成的东西。ask-codex 把它们接在一起，中间只补了“这次任务对应哪一轮”这一环。

Codex 这一端

借它自带的 app-tools

Codex 桌面应用自带一个插件，里面有 read_thread 和 send_message_to_thread。ask-codex 把它作为子进程启动来收发消息，不实现通信协议，也不往 Codex 里装任何东西。

Claude Code 这一端

借它的后台任务

等待由一个普通的 Node 进程承担，进程退出就是完成信号。通知和唤醒都是 Claude Code 自己的能力，ask-codex 没有写任何回调。

中间这一环

用请求编号找到那一轮

发送接口不返回轮次 ID。于是每次派发生成一个唯一编号写进消息正文，再从历史里反查出轮次并固定下来。之后只认这一轮：状态为 completed 才算完成，只取标记为最终答案的消息。Codex 不需要配合，不用主动回信。

出错的时候

只查，不重发

请求状态每一步都先落盘。派发结果不明时按编号去找，找不到就报错，不会自动再发一次。已完成的请求在 Codex 关闭后也能从本地缓存取回。

03 · 对比

和其他做法的区别

让两个编码助手协作的办法很多。ask-codex 只解决其中一个具体问题，换来的是几乎为零的接入成本。

做法用已有的桌面对话两端要装什么常驻进程结果怎么回来
直接调用 codex exec否，另起会话无无进程输出
MCP 或插件桥接多数是工具自己管理的会话注册 MCP 或安装插件通常有随会话运行的服务进程工具返回值或任务查询
消息代理部分支持，常需先注册会话通常两端都要装多数需要依赖对方主动回信
界面自动化是通常要注册 MCP视实现而定读取本地会话记录
ask-codex是无无按轮次状态自动取回最终回复

按常见技术路线归纳，具体项目各有差异。ask-codex 不是多 agent 编排框架，只负责 Claude Code 到 Codex 桌面对话这一个方向的任务调用。

04 · 命令

派发之后，还能看、能改、能停

派发

等待并输出最终回复。同一个对话可以反复调用。

ask-codex <threadId> "任务"

看进度

返回当前轮次状态和已有的中间回复。

ask-codex --status <requestId>

纠偏

向正在运行的这一轮补充要求，不用等它结束。

ask-codex --steer <requestId> "补充"

停止

和点击界面上的停止按钮走同一条路径，并校验轮次，不会误停下一轮。

ask-codex --stop <threadId>

恢复

等待进程被杀掉也没关系，按编号接着等，不会重发任务。

ask-codex --resume <requestId>

长消息

带引号、换行的长任务，从文件或 stdin 读取。

ask-codex <threadId> --stdin

05 · 开始

三步，不需要 npm install

  1. 在 Codex 桌面应用里打开目标对话，从链接 codex://threads/<threadId> 里取出 ID。

  2. 在项目目录里检查连接。

    node ask-codex.cjs --check

  3. 对 Claude Code 说一句话。

    用后台 Bash 运行 node ask-codex.cjs <threadId> "检查上传接口的并发问题"，Codex 回复后告诉我结论。

仅支持 Windows，需要 Node.js 20 或更高版本，以及正在运行的 Codex 桌面应用。

这是实验工具，依赖 Codex 桌面应用自带的 app-tools 插件和内部 IPC。它们不是公开接口，应用更新后可能需要适配。
